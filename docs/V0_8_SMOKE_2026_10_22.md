# v0.8 development smoke evidence — 22 October 2026

This is an unreleased development checkpoint. Published v0.7.0 EXEs do not contain these changes. All six provider requests used synthetic public developer fixtures and the configured Gemini credential. No personal resume, real microphone audio or actual desktop pixels were sent.

## Narrow live sample

Model: gemini-3.5-flash-lite. One request per case, no retry. Six cases passed their declared rubrics:

| Kind | Cases | Passed | Provider interval, nearest-rank p50 | Largest observed provider interval |
| --- | --- | --- | --- | --- |
| JavaScript | Numeric sort without mutation; Unicode code points; negative sliding windows | 3 / 3 | 5.087 s | 6.161 s |
| Screens | Small JavaScript code repair; intentionally blurred identifier requiring clarification | 2 / 2 | 2.165 s | 3.821 s |
| Grounding | Google Cloud skills do not establish Google employment | 1 / 1 | 1.690 s | 1.690 s |

The JavaScript answers and screen code repair were executed against finite tests in the separate restricted Node container, not in the desktop app. Median grading/execution interval for the three coding cases was 1.183 s. Expected results were not included in provider prompts; these fixtures and tests are nevertheless public.

These are six correlated developer smoke cases, not a private independent holdout, an accent benchmark, a general accuracy percentage or proof of 100% correctness. At these sample sizes the upper quantile is effectively the largest observed value. No first-token, semantic useful-answer, capture-to-answer or speech-end latency is inferred from these non-streaming calls. This was one Windows laptop with Docker Desktop and an uncharacterized internet connection.

Source hashes were recorded in every private receipt. Each kind's receipts shared one source-hash set during the smoke. Original receipts remain under ignored test-results; the content-free aggregate is frozen in V0_8_SMOKE_SUMMARY.json. Subsequent evaluator/reporting changes must not be treated as a fresh provider run.

## Evaluation infrastructure

- Public development corpus: 64 coding, 62 screen, 60 grounding/resume cases, plus 100 synthetic ASR clips and 100 routing sequences. Variants are correlated; added cases are explicitly development cases.
- Python, SQLite and JavaScript reference solutions passed the restricted Docker runner. Wrong results, numeric sorting/input mutation, syntax errors, infinite loops and excessive output are rejected.
- The Node and Python images are pinned by registry digest. The runner uses no network or host mounts, non-root execution, a read-only root filesystem and bounded CPU, memory, process count, output and execution time.
- This tests declared controls; containers are not a claim of perfect adversarial isolation. The desktop never executes generated solutions.
- An actual CLI pipeline test against a loopback provider covers correct JavaScript, wrong code, missing code fencing and HTTP 503 without replay. All attempts remain in the aggregate.
- Structured JSON grading rejects extra guessed answers and prose where the contract requires only the declared fields. Optional case-sensitive ASR critical-token grading preserves identifiers.
- Reports separate provider intervals from grading and total elapsed time, preserve failures/unattempted cases and leave missing historical stage timings unknown. They do not reconstruct missing first-token timings.

## Runtime recovery

Nine local UI/save scenarios include normal/delayed responses, one bounded retry, quota/authentication errors, connection reset, broken partial output, absent first response and a stalled partial stream.

The overlay reports prolonged waiting or a paused answer after approximately five seconds without progress, exposes Stop answer, suppresses retry while a request is active and preserves partial drafts on cancellation. These are observed-request states; no cloud health polling was added.

## Still required

A larger independent holdout, broader language/vision tasks, consented human accents/corrections/overlap, representative network distributions, model comparisons and fresh hardware/endurance qualification remain outstanding. Speed targets in the implementation plan remain proposed targets. No additional cloud requests are made automatically by the new reporting or fixture-preparation commands.
